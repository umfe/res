# Git 自动提交

仅在用户明确要求提交改动时执行本流程。完成本地提交，不推送远程。不得把创建、编辑或解释本技能本身视为要求执行提交。

## 定位仓库

1. 记录调用时的当前工作目录 `pwd`。使用 `git -C "<pwd>" rev-parse --show-toplevel` 判断它是否为仓库根目录或位于某个仓库的子目录。
2. 若成功，使用返回的仓库根目录；即使当前目录下面还有其他仓库，也不另行选择。
3. 仅当当前目录确实不在 Git 工作树内时，递归搜索 `pwd` 的子目录，包括隐藏目录。识别 `.git` 目录以及 `.git` 文件；后者用于 linked worktree 等工作树。用 Git 验证候选并取得真实的工作树根目录，规范化绝对路径并去重。不要进入 `.git` 内部，也不要通过链接跳到 `pwd` 之外。
4. 没有候选：说明未找到可提交的 Git 仓库并停止。只有一个候选：使用它。多个候选：列出绝对路径，必须询问用户指定哪个，等待回答后再继续。不得根据名称、排序、修改时间或改动数量自行猜选。
5. 裸仓库不能执行这里的工作树提交流程。权限错误、安全目录限制或其他 Git 故障也不能当作“没有仓库”；报告具体问题，不自动改写 Git 配置。

后续 Git 命令统一使用 `git -C "<仓库根目录>" ...`，不能只处理最初 `pwd` 子目录中的文件。读取所选仓库适用的 `AGENTS.md`、`CONTEXT.md` 及提交规范。

## 确定提交范围

先运行 `git status --short --untracked-files=all`，确认是否存在暂存、未暂存、未跟踪或冲突内容。存在未解决冲突，或正在进行 merge、rebase、cherry-pick 等操作时，停止并报告，不擅自继续或修复。

使用 `git diff --cached --quiet` 判断暂存区是否有差异：退出码 `1` 表示有差异，`0` 表示没有差异，其他退出码按错误处理。不要为了比较而强行引用 `HEAD`，这样尚无首次提交的仓库也能处理。

### 暂存区有改动

- 本次只分析并提交当前暂存区中的内容。
- 使用 `git diff --cached --name-status`、`git diff --cached --stat` 和 `git diff --cached` 理解实际变更。
- 不运行 `git add`，不使用 `git commit -a`，不把其他未暂存或未跟踪文件顺带加入。
- 部分暂存文件只提交已暂存的部分，保留工作树中剩余内容。

### 暂存区没有改动

- 若既没有未暂存的已跟踪改动，也没有未被忽略的未跟踪文件，说明没有可提交改动并停止，不创建空提交。
- 否则分析全部可提交改动：用 `git diff --name-status`、`git diff --stat`、`git diff` 查看已跟踪内容，用 `git ls-files --others --exclude-standard` 列出并检查未跟踪文件。
- “全部改动”包括已跟踪文件的修改、删除，以及未被 Git 忽略的新文件；不强行添加被忽略文件。
- 若发现疑似密钥、凭据或明显不应提交的内容，说明风险并询问用户，不擅自排除或提交。
- 分析后从仓库根目录执行 `git add -A`，再检查暂存区文件列表和 diff。提交信息必须以最终暂存内容为准。
- 子模块或嵌套仓库的内部改动不能由父仓库直接提交，不递归替它们提交；若只有此类不可直接提交内容，说明原因并停止。

## 生成提交信息

生成消息前，必须读取 [提交信息生成提示词](references/commit-message-prompt.md)，严格遵守其中的语言、Conventional Commits 格式、布局和行数限制。不得用近期提交历史推断的格式替代该提示词。

该提示词仅约束实际写入 Git 的提交信息，不约束对用户的结果说明。其中的“所有改动”仅指本次最终暂存区内容，不包括其他未暂存或未跟踪的改动。

- 基于最终暂存内容生成消息，不照抄提示词里的示例，不编造不存在的功能，也不声称未运行的测试已经通过。
- 若仓库强制提交规范与该提示词明确冲突，先说明冲突并询问用户，不擅自改用其他格式。
- 对二进制资源或无法可靠解读的内容，基于可确认的文件类型和操作描述，不猜测其内部变化。

## 自行提交

1. 如果仓库规定提交前检查，执行适用检查；失败时停止并说明。不要为完成提交顺手修改代码或暂存无关产物。
2. 提交前复查状态及暂存区差异。若提交范围发生变化，重新分析并更新提交信息；若暂存区最终为空，则不提交。
3. 生成完整提交信息后执行 `git -C "<仓库根目录>" commit -m "<完整提交信息>"`。将包含标题、英文行和详情的完整多行文本作为同一个 `-m` 参数安全传递；不要拆成多个 `-m`，因为 Git 会在它们之间插入额外空行，破坏规定布局。不要把 diff 内容拼成可执行 shell 代码。
4. 不额外询问“是否提交”；用户调用本流程就是对已确定范围的本地提交请求。多仓库选择、敏感内容以及实际执行工具的权限审批仍必须正常处理。
5. 不推送、不拉取、不 amend、不重写历史、不重置或清理工作树，不修改用户身份或仓库配置，不跳过提交 hooks。命令失败时保留现状，报告原因，不盲目重试或回滚用户内容。
6. 提交成功后读取最新提交的短哈希、标题，并重新检查 `git status --short --untracked-files=all`，确认实际结果与剩余改动。

## 结果说明

成功时简要报告所选仓库、提交范围（原有暂存区或全部改动）、提交哈希和提交信息，以及仍未提交的改动。无仓库、无改动或失败时，明确说明未创建提交及原因；已执行暂存但提交失败时也要说明暂存区保留了哪些变化。
